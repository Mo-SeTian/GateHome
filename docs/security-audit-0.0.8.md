# Gatehouse 0.0.8 登录与配置权限安全审查

审查日期：2026-10-08（Asia/Shanghai）。对象为当前工作区 0.0.8 源码；测试使用临时目录、虚构密码和本机临时 HTTP/HTTPS 服务。没有读取生产凭据，没有对实际公网或局域网部署发起攻击测试。

## 结论

没有在本次检查中发现无有效会话时，通过 SQL/JSON/命令注入、伪造代理头、修改请求方法或编码路径直接读取、修改配置的路径。但确认了一个**特定部署下可导致完整管理权限接管的会话泄露路径**，以及一个登录拒绝服务问题。不能将“未发现直接注入绕过”理解为“完全安全”。

本次交付审查报告和测试，没有更换登录协议、修改生产配置或发布新版本。下述风险仍存在于 0.0.8；需要按部署条件处置。

## 发现 1：同一主机名不同端口的服务可收到管理 Cookie（高风险，有前提）

- 位置：`internal/gateway/admin.go:328` 设置 `gatehouse_session`，`Path=/`；`internal/gateway/proxy.go:48` 转发请求时保留 Cookie；`internal/gateway/admin.go:258` 凭有效 Cookie 授予管理权限。
- 前提：管理入口与另一个不可信或已被攻陷的服务使用**同一个主机名、不同端口**；管理员登录后访问该服务，且协议满足 Cookie 的 Secure 条件。不是任意陌生域名都能收到 Cookie，也不是攻击者无需任何前提就能猜出会话。
- 证据：使用真实 TLS 管理服务器、TLS 反代入口、CookieJar 和受控上游，在同一测试域名的两个端口间自动发送 Cookie。上游取得 Cookie 后，独立请求 `GET /api/config` 返回 200，`PUT /api/config` 返回 200，临时配置名称确实改变。全过程没有输出会话值。独立主机名没有收到该 Cookie。
- 原因：Cookie 不按端口隔离。HttpOnly 阻止页面脚本读取 Cookie，但不阻止服务器收到 Cookie；Secure 只约束传输协议；SameSite 不能隔离同一站点的不同端口。固定值 `X-Gatehouse-Request: 1` 和 Origin 检查用于约束浏览器跨站请求，无法阻止持有被盗 Cookie 的非浏览器客户端重放。
- 处置：管理界面使用专用主机名，例如 `gate.example.com`，其他服务使用 `nas.example.com` 等不同主机名；管理主机名的所有端口都应由可信服务占用。同一 IP 上仅用不同端口区分服务也不应视为 Cookie 隔离。公网管理使用 HTTPS，后端 HTTP 监听只开放给可信代理或隧道。
- 应用层后续加固：若必须支持同主机名多服务，应将管理认证改为不会自动发往其他端口的、按源隔离的认证机制，或增加独立会话证明并验证整个读取/写入流程；仅改 Cookie 名、Path 或增加 HttpOnly 不足以解决。直接在所有反代请求中删除管理 Cookie 会破坏当前“反代 Gatehouse 自身”的功能，且不能保护绕过 Gatehouse 的其他同名服务，因此不能作为完整修复。
- 依据：[RFC 6265 §8.5](https://httpwg.org/specs/rfc6265.html#weak-confidentiality) 明确指出 Cookie 不提供端口隔离。

## 发现 2：全局共享登录限流允许远程锁住其他用户登录（中风险）

- 位置：`internal/gateway/admin.go:280`，`attempts` 是整个 Admin 实例共享的时间列表，阈值为每分钟 8 次。
- 证据：一个来源提交 8 次错误密码后，另一来源提交正确密码也返回 429。重复消耗额度可以持续干扰新登录；已有会话不受此限流影响。
- 影响：拒绝服务，不会直接获得查看或修改配置的权限。
- 后续修复方向：按可信的实际来源限流并保持有限内存，结合有界并发控制，避免所有用户共用一个极低阈值。通过反代部署时，不能直接信任任意客户端提交的 `X-Forwarded-For`，也不能简单按后端看到的同一个代理 IP 分桶，否则仍会共享锁定。

## 部署风险：明文 HTTP 登录可被链路攻击者窃取凭据

管理监听本身为 HTTP；`secureSession` 在直连 HTTP 时不设置 Secure，公网访问配置也允许 `http://` 地址。这与项目保留的可信局域网使用方式一致，但不适合直接暴露公网或不可信网络。能够监听或篡改链路的攻击者可获取密码/会话并接管配置。这是部署条件下的凭据泄露，不是 JSON 或数据库注入。

公网入口应使用独立域名的 HTTPS，并限制明文管理端口的网络可达性；不要只在设置里添加一个 HTTP 公网地址就认为连接已获得加密保护。此次没有验证实际服务器的映射、代理 TLS 或防火墙配置。

## 已检查并通过的边界

| 检查项 | 结果与证据 |
| --- | --- |
| 管理 API 鉴权 | 21 个方法/路径组合 × 3 种无效会话，全部返回 401，持久配置不变。覆盖配置读写、状态、日志、统计、DNS、任务、备份、上传检查、更新、恢复、重启和退出。 |
| 代理头伪造 | 伪造回环 IP、转发用户、转发协议以及 Bearer 字段，不能替代有效会话。 |
| 登录注入 | SQL 字符串、NoSQL 对象、命令字符串、HTML、null、额外 JSON 字段、拼接 JSON 均不创建会话；正常登录仍成功。密码直接交给 bcrypt 比较，无 SQL 或 shell 拼接。 |
| 路径和方法混淆 | 15 种路径 × 9 种方法，共 135 个组合；包括编码、重复分隔符、路径穿越、分号、空字节和磁盘敏感文件路径，没有返回配置或成功写入。规范化重定向仍需鉴权。 |
| CSRF / CORS | 缺少专用请求头、不支持的内容类型、恶意 Origin、null Origin 的写请求被拒绝；跨站预检不授予 CORS 权限。现有反代测试确认白名单不免除登录。 |
| 会话 | 32 字节随机令牌、服务端存储哈希、12 小时到期；过期、退出和新 Admin 实例不接受旧会话。新测试与既有测试共同覆盖。 |
| XSS | 检查日志、事件、配置文本、表格及 SVG 渲染；10 个恶意日志/事件渲染用例保持 HTML 转义。既有 SVG 测试验证名称转义。CSP 不允许内联脚本，页面禁止被嵌入框架。这些用例为字符串渲染测试，不等于完整浏览器 XSS 模糊测试。 |
| 文件/上传入口 | 静态服务只开放 HTML/JS/CSS，不挂载数据目录；上传和备份在会话校验后处理。ZIP 路径规范化、特殊文件、重复路径、大小限制、完整性检查与备份篡改测试已检查。 |
| SSRF 与命令执行 | 上游、订阅、网络探测配置需要登录；未找到未登录者可指定任意出站地址的管理入口。监督进程使用参数化 `exec.Command`，未找到来自登录输入的 shell 执行路径。 |
| 凭据回显 | 配置 API 返回凭据是否配置，不返回 DNS Token、代理密码或密码哈希。备份包含凭据，但需要有效会话并加密导出。 |

更新包的 SHA-256 校验验证内容完整性，不能认证发布者身份；这在现有界面已有说明。上传/应用更新需要登录，不能据此认定为未登录绕过。管理员必须使用可信来源的更新包。

另外，前端 `showLogin()` 隐藏旧界面但没有彻底清空旧 DOM 和所有内存缓存。退出后的**同一浏览器上下文**中，开发者工具仍可能查看此前已经加载的数据；这不是远程未登录读取 API，但共享设备应关闭管理标签页。应用层可后续清空界面与缓存，并取消未完成请求。

模块层面提示 [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932)，涉及 `golang.org/x/crypto/openpgp`；本项目未导入或调用该包。没有为了消除无关模块提示盲目替换 bcrypt/scrypt 所在依赖。扫描结果是当时漏洞库与静态调用分析的结果，不是不存在未知漏洞的证明。
